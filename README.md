# LogWise · LLM 智能日志诊断助手

粘贴一段线上报错日志 → LLM 返回结构化诊断（错误类型 / 根因 / 影响范围 / 排查步骤 / 置信度），SSE 流式输出。

`Python 3.11` · `FastAPI` · `DeepSeek` · `pytest 198 项` · `Docker` · `Kubernetes`

---

## 先说结论：三个技术决策，其中一个是「不采用」

这个项目的重点不是功能列表，而是**每个设计选择都有数据支撑**。

| # | 问题 | 结论 | 数据 |
| --- | --- | --- | --- |
| 1 | 一次故障产生多条日志，只送第一条 ERROR 够吗？ | ✅ **采用**上下文聚合 | 多日志场景命中率 **16.7% → 100%**，成本仅 +1.4% |
| 2 | Prompt 加 Few-shot、加 `evidence` 字段值不值？ | ✅ **采用** Prompt v3 | 成本 +80%，换来「信息不足时的诚实率」**50% → 100%**；证据零编造 59/59 |
| 3 | RAG / 向量检索能提升诊断质量吗？ | ❌ **不采用**（默认关闭） | 三套后端都实现了：成本 **+53~81%**，准确率 **提升 0** |

第 3 条的结论是负面的，**但过程才是重点**：

- 实现了 **BM25 / 向量 / RRF 融合三套可插拔检索后端**，建了 53 条案例知识库
- 挖出一个反直觉的成本坑：**动态注入的内容会打断 Prompt 前缀缓存**
  —— 缓存命中率从 90% 掉到 39%，所以"token 更少"反而"更贵"
  （判断 RAG 贵不贵，不能看 token 数量，要看**缓存命中率**）
- 定位到 RAG 的适用边界：**它只对「模型不知道的知识」有价值**。
  通用故障模式（磁盘满、NPE、Redis 连不上）模型本来就会，喂过去只是白花钱

> 过程中还修掉一处**评测集数据泄漏**：3 条用例与 Few-shot 示例撞了场景，等于开卷考。
> 修完并加了自动绊线（异常消息归一化成骨架再比对，撞车即测试失败）。

```bash
python app\run.py        # 或直接在文件管理器里双击
```

端口被占用时顺延到下一个可用端口。

需要从 `.env.example` 复制出 `.env`，填入一个 `DEEPSEEK_API_KEY`。

## 工程细节

### 上下文聚合：解决「第一条 ERROR 不是根因」

一次故障会产生多条日志。原实现只挑第一条 ERROR 送进模型，其余丢弃 ——
在评测集 6 条专门设计的用例上，命中率只有 **16.7%**。

改成**分层选择**（不依赖日志格式、不做语义关联）：

1. **锚点** —— 必含，第一条 CRITICAL/ERROR
2. 窗口内（±8 条）的 WARN 及以上
3. 窗口内的普通日志（如发布通知这类 INFO）
4. 窗口外的 WARN/ERROR（离得远但可能是真因）

超过上限 20 条时按上述优先级淘汰，**锚点必留**；最终按原始顺序输出 ——
时间线本身就是诊断线索。参数由四组扫描选定，结果是一条干净的单调梯度：
**10% → 60% → 80% → 100%**。

### 成本度量：三档计价

DeepSeek 会自动缓存重复出现的 Prompt 前缀。最初按「全部输入 × 全价」计算，
**成本高估约 1/3**。现在按「缓存命中 / 未命中 / 输出」三档分别计价，
流式接口也能拿到**真实** token 数（`stream_options={"include_usage": True}`）。

单价不硬编码 —— DeepSeek 调价频繁且分高峰/空闲时段，`/stats` 会回显当前生效的单价。

### 接口防护

鉴权（`X-API-Key`，本机回环地址豁免）+ 令牌桶限流（默认 20 次/60 秒）+ 结果缓存。

缓存键 = `归一化日志 + 模型名 + Prompt 版本 + 聚合参数 + 检索结果指纹` ——
**任一变化旧缓存自动失效**。这是缓存类功能最隐蔽的坑：
改了 Prompt 却命中旧缓存，你会以为「改了没效果」。
