# 踩坑记录

按时间顺序记录真实排障过程。每条都写清了**现象 → 原因 → 修法**，以及留下的回归测试（如果有）。

---

## 1. SSE 流式输出变成"攒到最后一次性吐出"

**现象**：`/diagnose/stream` 接口虽然写成了 SSE，但浏览器侧要等到模型完全生成完，才一次性看到全部内容。

**原因**：在 async 生成器里用**同步**的 OpenAI 客户端迭代：

```python
for chunk in sync_client.chat.completions.create(..., stream=True):   # ❌ 阻塞事件循环
    yield chunk
```

同步网络 IO 会阻塞整个事件循环，uvicorn 无法在生成过程中把数据刷出去。

**修法**：改用 `AsyncOpenAI` + `async for`，保证流式过程里**没有任何同步 IO**。

---

## 2. openai SDK 大版本升级破坏流式

**现象**：升级到 openai 3.x 后，流式行为异常。

**原因**：3.x 更换了 httpx2 传输栈，与本项目的流式用法不兼容。

**修法**：`requirements.txt` 固定 `openai>=1.40,<2`。

> 教训：依赖不锁上界，某天 `pip install` 就会把你带到一个没测过的世界。

---

## 3. K8s 更新镜像后 pod 仍在跑旧代码

**现象**：`docker build` 出了新镜像、`kubectl rollout restart` 也执行了，但 pod 行为没变。

**原因**：**Docker Desktop 的 K8s 使用独立的 containerd 镜像缓存**，Docker 引擎里构建的镜像不会自动同步进去。在 `imagePullPolicy: IfNotPresent` 下，`latest` 这个 tag 会命中旧缓存。

**修法**：每次构建打**唯一 tag**（如 `v2`），并让 deployment 指向该 tag。

> 与本项目另一个「改了代码没生效」的问题（见第 6 条）同源：
> **缓存与 tag 的复用，会让"我明明改了"变成一个假象。**

---

## 4. Few-shot 示例被模型当成了真实历史

**现象**：把 Few-shot 从 1 个扩到 4 个之后，模型在根因里写出了这样的话：

> 「…与 2026-04-02 的日报导出失败是同一类问题…」

**原因**：这是幻觉。模型把 Few-shot 示例里的**日期与案例**当成了这个系统的真实历史。
触发条件是其中一个示例（磁盘写满）与待诊断日志**场景撞车**。

**修法**：在 System Prompt 里加一段明确约束 ——
「示例仅用于说明输出格式，与当前日志无关，不要引用其中的时间、模块或结论」。

修复后连跑 6 次全部干净，并加了回归测试（`tests/test_prompts.py`）。

> 这个坑的启发：**Few-shot 不只是"教格式"，它同时也在污染模型的上下文。**
> 示例的场景距离待诊断场景越近，越容易被误当作事实。

---

## 5. 成本统计漏算了上下文缓存，高估约 1/3

**现象**：最初的成本数字比实际账单高。

**原因**：DeepSeek 会自动缓存**重复出现的 Prompt 前缀**（System Prompt + Few-shot 每次请求都一样），
命中部分的输入单价远低于未命中。而最初按「全部输入 × 全价」计算。

实测 `usage` 结构：

```
prompt_tokens: 543
  ├─ prompt_cache_hit_tokens : 384   ← 命中缓存，单价低得多
  └─ prompt_cache_miss_tokens: 159
```

**修法**：记录 `prompt_cache_hit_tokens`，按**三档价格**（缓存命中 / 未命中 / 输出）分别计价。

> 这个坑在 RAG 那一轮还演化出了一个反直觉结论：
> **动态注入的内容会打断缓存前缀**，导致"token 更少却更贵"。
> 见 [`EXPERIMENTS.md` §5.5](EXPERIMENTS.md#55-一个反直觉的成本发现)。

## 6. 改了 Python 代码，服务行为没变（页面却是新的）

**现象**：前端报两个错 —— `POST /context` 返回的不是数组（前端读 `.map` 报 TypeError）、
`POST /diagnose/stream` 返回 `405 Method Not Allowed`。

**原因**：**Python 代码在启动时载入内存，`static/index.html` 是每次请求现读磁盘的。**
于是出现了「页面是新版、接口是旧版」的错位：前端改用 POST，而旧后端只认 GET。

**修法**：

1. 关掉旧进程重新启动（代码改动必须重启）
2. 演示页加**服务端版本自检** —— 页面加载时探测新接口，是旧版就在顶部显示黄色提示条，
   并写明该怎么办；遇到 404/405 时也给人话而不是错误码

> 这条和 K8s 那条（第 3 条）是同一类问题的两个面：
> **运行中的进程与磁盘上的代码不一致，是个很容易被误判成"代码有 bug"的状态。**

## 7. 只取第一条 ERROR 导致主因误判

**现象**：一次故障通常产生多条日志，而 `_pick_target()` 只挑第一条 ERROR 送进模型，其余丢弃。

**量化**：评测集里 6 条专门设计的用例上，命中率只有 **16.7%**；
把全部日志都送进去可以达到 **100%** —— 差距 83 个百分点，而成本只涨 11.8%。

典型对照：

| 用例 | 只看第一条 ERROR | 看到全部日志后 |
| --- | --- | --- |
| Pod 驱逐 | 网关调用订单服务连接被拒绝 | 节点内存不足触发 Pod 驱逐 |
| 磁盘写满 | 上游依赖返回 503，服务不可用 | 磁盘写满导致本地缓存子系统不可用 |

**修法**：实现分层上下文聚合（`app/context.py`），参数经四组扫描选定。
详见 [`EXPERIMENTS.md` §4](EXPERIMENTS.md#4-上下文聚合)。

## 8. 评测指标会饱和

**现象**：第一版评测集只有 20 条常规用例，Prompt 新旧两版**都是 100%**，完全测不出差异。
更糟的是，如果没意识到这一点，会得出"这次 Prompt 改动没有副作用也没有收益"的错误结论。

**原因**：日志里的异常类名（`OutOfMemoryError`、`No space left on device`）本身信息量太足，
模型只要读懂英文再归类就行 —— 对模型来说太简单了。

**修法**：补 `tricky`（真因藏在 `Caused by` 里）、`vague`（信息不足，考察是否敢说"不知道"）
两档难题。后续又补了 `multi` / `noise` 两档。

> **设计评测集时要先问一句：这个指标会饱和吗？**
> 一个测不出差异的评测集，比没有评测集更危险 —— 它会让你以为自己做了验证。

## 9. 评测集与 Few-shot 的数据泄漏

**现象**：设计检索功能前做自检，发现 38 条评测用例里有 3 条与 Few-shot 示例撞了场景 ——
其中 `res-01` 与示例2 **两行日志逐字相同**，`cfg-03` 与示例4 的**异常消息骨架完全一样**
（只有参数不同）。这几条在历次评测里都是满分，但考的是"能否对照示例抄答案"。

**修法**：换成 Few-shot 未覆盖的故障类型，并加绊线 ——
`test_no_shared_exception_template` 把异常消息归一化成骨架
（抹掉引号内的取值、类名、数字）再比对，撞车即失败。

> **做 RAG 时这个坑会放大**：知识库若直接用评测集建，等于把答案抄进课本再考同一张卷子，
> 测出来的提升必然是假的。所以顺序必须是：**先修泄漏 → 再建库 → 再谈提升。**

## 10. 检索层踩到的两个坑

**① query 侧词频被线性放大**

长日志噪音用例里有 10 条「健康检查通过」。早期实现按出现次数累加，
该词权重被放大 10 倍，把一条恰好含相同噪音的案例顶到检索第一（**760 分**），
真正该命中的案例排第 4。

修法：**query 侧二值化**（用 `set` 而不是 `Counter`）—— 检索只关心"出现了哪些错误"，
不关心同一个词重复几次。词频的作用体现在文档侧（`tf`），不体现在查询侧。

**② 无信息量的日志行没有被过滤**

同上。健康检查 / 指标上报这类行在故障上下文里没有任何区分度，却能在数量上压倒异常行。
现在在**查询与文档两端**的 token 化阶段都跳过它们。

两个修正加上补充案例的合计效果：Recall@3 **81.2% → 97.1%**，Precision@1 **62.5% → 85.3%**。

## 11. 长日志被 URL 长度限制挡住

**现象**：粘贴大日志（如 `data/HDFS_2k.log`，28 万字符）时接口直接 400。

**原因**：前端原本用 `GET /diagnose/stream?text=...` 把日志放在 query string 里。
实测上限约 **32K 字符**。

**讽刺之处**：「日志很长」恰恰是上下文聚合最有价值的场景 ——
日志短的时候反正全选，看不出聚合有什么用；只有长日志才能看出筛选效果，而长日志传不过去。

**修法**：两个文本接口都提供 POST 版本（JSON body，无长度限制），GET 版保留向后兼容，前端统一改用 POST。

## 12. `/context` 在大日志下撑爆浏览器

**现象**：`/context` 原本返回全部日志供前端展示。2 万条日志时响应体约 **4 MB**、
前端要渲染 **2 万行 DOM**，浏览器会卡死。

**修法**：展示上限 500 条（优先保留锚点附近与**被选中**的那些）。
**只影响展示，不影响实际送给模型的日志**（那由 `app.context` 决定）。
同时给前端加了 `id="ctxCard"` 之外的分支提示，说明"已限制展示"。

---

## 13. Python 默认参数在定义时求值

**现象**：单元测试里替换 `INDEX_PATH` 不生效。

**原因**：`def from_index(cls, path: Path = INDEX_PATH)` 这种写法下，
默认值在**函数定义时**就绑定好了，之后替换模块级变量没用。

**最阴的地方**：这个 bug **只有索引建好之后才会暴露** ——
建索引前必然抛 `IndexNotBuiltError` → 走降级分支 → 测试通过；
索引一建好就不降级了 → 测试失败。

**修法**：所有路径参数改成 `None` 默认值，在函数体内解析。

---

## 14. 三个"假向量测不出来"的 bug

用假向量跑通全链路之后，以为代码没问题；**用户一填真实 Key，立刻暴露三个问题**：

1. **`build_index.py` 读不到 `.env`** —— `load_dotenv()` 原来只写在 `diagnose.py` 里，
   而这个脚本不经过它。表现是"诊断功能正常、手工测试也正常，就它说没配 Key"。
   **修法：谁消费配置谁负责加载**（改到 `app/embedding.py` 里）。

2. **`estimate_tokens_from_chars` 参数传错** —— 它收的是**字符数**不是文本，
   我把整段日志传进去了，直接 `TypeError`。

3. **默认参数陷阱**（同第 13 条）。

> 教训：**假数据的端到端测试有边界** —— 它验证了算法与数据流，但验证不了
> 真实配置路径（读 env、真实网络、真实返回结构）。
> 所以"先假后真"这个流程必须真的走到"真"那一步才算完成。
