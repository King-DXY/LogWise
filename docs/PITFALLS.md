# 踩坑记录

按时间顺序记录真实排障过程。每条都写清了**现象 → 原因 → 修法**，以及留下的回归测试（如果有）。

---

## 1. SSE 流式输出变成"攒到最后一次性吐出"

**现象**：`/diagnose/stream` 接口虽然写成了 SSE，但浏览器侧要等到模型完全生成完，才一次性看到全部内容。

**原因**：在 async 生成器里用**同步**的 OpenAI 客户端迭代：

```python
for chunk in sync_client.chat.completions.create(..., stream=True):   # ❌ 阻塞事件循环
    yield chunk
```

同步网络 IO 会阻塞整个事件循环，uvicorn 无法在生成过程中把数据刷出去。

**修法**：改用 `AsyncOpenAI` + `async for`，保证流式过程里**没有任何同步 IO**。

---

## 2. openai SDK 大版本升级破坏流式

**现象**：升级到 openai 3.x 后，流式行为异常。

**原因**：3.x 更换了 httpx2 传输栈，与本项目的流式用法不兼容。

**修法**：`requirements.txt` 固定 `openai>=1.40,<2`。

> 教训：依赖不锁上界，某天 `pip install` 就会把你带到一个没测过的世界。

---

## 3. K8s 更新镜像后 pod 仍在跑旧代码

**现象**：`docker build` 出了新镜像、`kubectl rollout restart` 也执行了，但 pod 行为没变。

**原因**：**Docker Desktop 的 K8s 使用独立的 containerd 镜像缓存**，Docker 引擎里构建的镜像不会自动同步进去。在 `imagePullPolicy: IfNotPresent` 下，`latest` 这个 tag 会命中旧缓存。

**修法**：每次构建打**唯一 tag**（如 `v2`），并让 deployment 指向该 tag。

> 与本项目另一个「改了代码没生效」的问题（见第 6 条）同源：
> **缓存与 tag 的复用，会让"我明明改了"变成一个假象。**

---

## 4. Few-shot 示例被模型当成了真实历史

**现象**：把 Few-shot 从 1 个扩到 4 个之后，模型在根因里写出了这样的话：

> 「…与 2026-04-02 的日报导出失败是同一类问题…」

**原因**：这是幻觉。模型把 Few-shot 示例里的**日期与案例**当成了这个系统的真实历史。
触发条件是其中一个示例（磁盘写满）与待诊断日志**场景撞车**。

**修法**：在 System Prompt 里加一段明确约束 ——
「示例仅用于说明输出格式，与当前日志无关，不要引用其中的时间、模块或结论」。

修复后连跑 6 次全部干净，并加了回归测试（`tests/test_prompts.py`）。

> 这个坑的启发：**Few-shot 不只是"教格式"，它同时也在污染模型的上下文。**
> 示例的场景距离待诊断场景越近，越容易被误当作事实。

---

## 5. 成本统计漏算了上下文缓存，高估约 1/3

**现象**：最初的成本数字比实际账单高。

**原因**：DeepSeek 会自动缓存**重复出现的 Prompt 前缀**（System Prompt + Few-shot 每次请求都一样），
命中部分的输入单价远低于未命中。而最初按「全部输入 × 全价」计算。

实测 `usage` 结构：

```
prompt_tokens: 543
  ├─ prompt_cache_hit_tokens : 384   ← 命中缓存，单价低得多
  └─ prompt_cache_miss_tokens: 159
```

**修法**：记录 `prompt_cache_hit_tokens`，按**三档价格**（缓存命中 / 未命中 / 输出）分别计价。

> 这个坑在 RAG 那一轮还演化出了一个反直觉结论：
> **动态注入的内容会打断缓存前缀**，导致"token 更少却更贵"。
> 见 [`EXPERIMENTS.md` §5.5](EXPERIMENTS.md#55-一个反直觉的成本发现)。

---

## 6. 改了 Python 代码，服务行为没变（页面却是新的）

**现象**：前端报两个错 —— `POST /context` 返回的不是数组（前端读 `.map` 报 TypeError）、
`POST /diagnose/stream` 返回 `405 Method Not Allowed`。

**原因**：**Python 代码在启动时载入内存，`static/index.html` 是每次请求现读磁盘的。**
于是出现了「页面是新版、接口是旧版」的错位：前端改用 POST，而旧后端只认 GET。

**修法**：

1. 关掉旧进程重新启动（代码改动必须重启）
2. 演示页加**服务端版本自检** —— 页面加载时探测新接口，是旧版就在顶部显示黄色提示条，
   并写明该怎么办；遇到 404/405 时也给人话而不是错误码

> 这条和 K8s 那条（第 3 条）是同一类问题的两个面：
> **运行中的进程与磁盘上的代码不一致，是个很容易被误判成"代码有 bug"的状态。**

## 7. 只取第一条 ERROR 导致主因误判

**现象**：一次故障通常产生多条日志，而 `_pick_target()` 只挑第一条 ERROR 送进模型，其余丢弃。

**量化**：评测集里 6 条专门设计的用例上，命中率只有 **16.7%**；
把全部日志都送进去可以达到 **100%** —— 差距 83 个百分点，而成本只涨 11.8%。

典型对照：

| 用例 | 只看第一条 ERROR | 看到全部日志后 |
| --- | --- | --- |
| Pod 驱逐 | 网关调用订单服务连接被拒绝 | 节点内存不足触发 Pod 驱逐 |
| 磁盘写满 | 上游依赖返回 503，服务不可用 | 磁盘写满导致本地缓存子系统不可用 |

**修法**：实现分层上下文聚合（`app/context.py`），参数经四组扫描选定。
详见 [`EXPERIMENTS.md` §4](EXPERIMENTS.md#4-上下文聚合)。

---

## 8. 评测指标会饱和

**现象**：第一版评测集只有 20 条常规用例，Prompt 新旧两版**都是 100%**，完全测不出差异。
更糟的是，如果没意识到这一点，会得出"这次 Prompt 改动没有副作用也没有收益"的错误结论。

**原因**：日志里的异常类名（`OutOfMemoryError`、`No space left on device`）本身信息量太足，
模型只要读懂英文再归类就行 —— 对模型来说太简单了。

**修法**：补 `tricky`（真因藏在 `Caused by` 里）、`vague`（信息不足，考察是否敢说"不知道"）
两档难题。后续又补了 `multi` / `noise` 两档。

> **设计评测集时要先问一句：这个指标会饱和吗？**
> 一个测不出差异的评测集，比没有评测集更危险 —— 它会让你以为自己做了验证。

## 9. 评测集与 Few-shot 的数据泄漏

**现象**：设计检索功能前做自检，发现 38 条评测用例里有 3 条与 Few-shot 示例撞了场景 ——
其中 `res-01` 与示例2 **两行日志逐字相同**，`cfg-03` 与示例4 的**异常消息骨架完全一样**
（只有参数不同）。这几条在历次评测里都是满分，但考的是"能否对照示例抄答案"。

**修法**：换成 Few-shot 未覆盖的故障类型，并加绊线 ——
`test_no_shared_exception_template` 把异常消息归一化成骨架
（抹掉引号内的取值、类名、数字）再比对，撞车即失败。

> **做 RAG 时这个坑会放大**：知识库若直接用评测集建，等于把答案抄进课本再考同一张卷子，
> 测出来的提升必然是假的。所以顺序必须是：**先修泄漏 → 再建库 → 再谈提升。**

---

## 10. 检索层踩到的两个坑

**① query 侧词频被线性放大**

长日志噪音用例里有 10 条「健康检查通过」。早期实现按出现次数累加，
该词权重被放大 10 倍，把一条恰好含相同噪音的案例顶到检索第一（**760 分**），
真正该命中的案例排第 4。

修法：**query 侧二值化**（用 `set` 而不是 `Counter`）—— 检索只关心"出现了哪些错误"，
不关心同一个词重复几次。词频的作用体现在文档侧（`tf`），不体现在查询侧。

**② 无信息量的日志行没有被过滤**

同上。健康检查 / 指标上报这类行在故障上下文里没有任何区分度，却能在数量上压倒异常行。
现在在**查询与文档两端**的 token 化阶段都跳过它们。

两个修正加上补充案例的合计效果：Recall@3 **81.2% → 97.1%**，Precision@1 **62.5% → 85.3%**。

---

## 11. 长日志被 URL 长度限制挡住

**现象**：粘贴大日志（如 `data/HDFS_2k.log`，28 万字符）时接口直接 400。

**原因**：前端原本用 `GET /diagnose/stream?text=...` 把日志放在 query string 里。
实测上限约 **32K 字符**。

**讽刺之处**：「日志很长」恰恰是上下文聚合最有价值的场景 ——
日志短的时候反正全选，看不出聚合有什么用；只有长日志才能看出筛选效果，而长日志传不过去。

**修法**：两个文本接口都提供 POST 版本（JSON body，无长度限制），GET 版保留向后兼容，前端统一改用 POST。

---

## 12. `/context` 在大日志下撑爆浏览器

**现象**：`/context` 原本返回全部日志供前端展示。2 万条日志时响应体约 **4 MB**、
前端要渲染 **2 万行 DOM**，浏览器会卡死。

**修法**：展示上限 500 条（优先保留锚点附近与**被选中**的那些）。
**只影响展示，不影响实际送给模型的日志**（那由 `app.context` 决定）。
同时给前端加了 `id="ctxCard"` 之外的分支提示，说明"已限制展示"。

---

## 13. Python 默认参数在定义时求值

**现象**：单元测试里替换 `INDEX_PATH` 不生效。

**原因**：`def from_index(cls, path: Path = INDEX_PATH)` 这种写法下，
默认值在**函数定义时**就绑定好了，之后替换模块级变量没用。

**最阴的地方**：这个 bug **只有索引建好之后才会暴露** ——
建索引前必然抛 `IndexNotBuiltError` → 走降级分支 → 测试通过；
索引一建好就不降级了 → 测试失败。

**修法**：所有路径参数改成 `None` 默认值，在函数体内解析。

---

## 14. 三个"假向量测不出来"的 bug

用假向量跑通全链路之后，以为代码没问题；**用户一填真实 Key，立刻暴露三个问题**：

1. **`build_index.py` 读不到 `.env`** —— `load_dotenv()` 原来只写在 `diagnose.py` 里，
   而这个脚本不经过它。表现是"诊断功能正常、手工测试也正常，就它说没配 Key"。
   **修法：谁消费配置谁负责加载**（改到 `app/embedding.py` 里）。

2. **`estimate_tokens_from_chars` 参数传错** —— 它收的是**字符数**不是文本，
   我把整段日志传进去了，直接 `TypeError`。

3. **默认参数陷阱**（同第 13 条）。

> 教训：**假数据的端到端测试有边界** —— 它验证了算法与数据流，但验证不了
> 真实配置路径（读 env、真实网络、真实返回结构）。
> 所以"先假后真"这个流程必须真的走到"真"那一步才算完成。

# 第一次全库排查（15~18）

## 15. "试跑"选项把生产数据覆盖了

**现象**：`build_index.py --limit N` 的 help 写的是"只处理前 N 条（用于小规模试跑）"，
但代码是 `cases = cases[:N]` → 只算出 N 条向量 → **`INDEX_PATH.write_text(...)` 整文件覆盖**。

于是跑一次 `--limit 5` 试跑，完整的 53 条索引就变成了 5 条，
之后 dense 检索报"索引缺少 48 条"。

**修法**：改成**与已有索引合并**（`{**old_vectors, **vectors}`），
并在维度或模型不一致时只提示、不擅自合并，要求显式加 `--force`。

> 教训：**一个"只是想试试"的动作不该破坏已有数据。** 凡是带"试跑/限制"语义的开关，
> 都要问一句：它写出的是完整结果还是部分结果？部分结果会覆盖谁？

## 16. 向量维度不匹配时静默算出错误的分数

**现象**：索引文件里存了 `model` 和 `dimensions`，但 `DenseRetriever.from_index`
只读 `vectors`，**从不校验**。

余弦相似度是 element-wise 的 `zip` 点积，**两边长度不一致时 `zip` 会静默截断到较短的那个** ——
不报错、正常返回结果，只是分数是错的。实测 4 维 query 对 8 维索引：

```
❌ 没有报错 —— 返回了 2 条结果
     a-01  score=0.100499   ← 只在前 4 维上算的
```

触发场景很现实：改了 `.env` 里的 `EMBEDDING_MODEL` 或 `EMBEDDING_DIMENSIONS`，忘了重建索引。

**修法**：加载时校验 ①向量彼此等长 ②`dimensions` 与实测一致 ③`model` 与当前配置一致，
不匹配就抛 `IndexNotBuiltError`（服务端会降级回 BM25 并把原因写进 `/stats`）；
`search()` 再加一道 query 维度守卫，不一致直接返回空 —— 宁可少给结果，也不给错的。

> 教训：**`zip` 是"静默截断"的重灾区。** 凡是用它做数值计算的场合，
> 都要先断言两边长度一致。

## 17. 指标在说假话

三处，都是"数字看起来正常，但含义和名字对不上"：

| 字段 | 原来的算法 | 问题 |
| --- | --- | --- |
| `requests.llm_calls` | `endpoint.startswith("/diagnose")` | 缓存命中和"没解析到日志"也走 `/diagnose`，它们**一次模型都没调**。指标名说"模型调用次数"，实际是"diagnose 请求数" |
| `requests.billable_calls` | `llm_calls - cache_hits` | 模型调用失败不产生 token（成本 0），却仍被算成"计费调用"，导致 `avg_per_billable_call` 被低估 |
| `latency_ms.p95` | `sorted[int(len*0.95)]` | nearest-rank 少减了 1。而 `RECENT_LIMIT=20`，于是**样本 ≤20 时 p95 恒等于 max** |

**修法**：`llm_call` 由调用方显式传入；`billable_calls` 用独立计数器（判据是 `cost > 0`）；
p95 改用 `ceil(0.95n)`。

> 教训：**指标名就是契约。** 一个名字叫 `llm_calls` 的字段如果实际是"请求数"，
> 它比没有这个字段更糟 —— 读的人会基于错误的理解做决策。

## 18. 一个不生效的配置项和一个恒真的测试

- `LOGWISE_CACHE_ENABLED=false` **不起作用** —— 只有 `snapshot()` 读了它（用于显示），
  `get()` / `set()` 完全没检查。等于一个"显示成已关闭"的开关。
- `DiagnosisCache.clear()` 只清数据不清计数，而 `/stats/reset` 的返回消息写的是
  「统计与缓存已清零」—— 做对照实验时上一轮的 hits/misses 会混进来。
- 测试 `test_context_does_not_touch_the_model` 的断言是 `assert after >= before`，
  **恒为真**，而且当时 `/context` 压根不写度量，`after == before` 是恒定的。
  它给了一种"这件事被测过了"的虚假安全感。

**修法**：开关在 get/set 里生效；新增 `reset()` 清数据+计数（`clear()` 保留计数并在
docstring 里写明区别）；那条空断言改成逐项比对。

> 教训：**看到 `assert a >= b` 这种宽松断言要警觉。** 问一句"什么情况下它会失败"，
> 如果答不上来，它就没在测任何东西。

# 第二次全库排查（19~20）

## 19. 模型返回一句大白话，接口就把 Python 异常原文甩给用户

**现象**：偶发 502，响应体是：

```json
{"detail":"模型调用失败：JSONDecodeError: Expecting value: line 1 column 1 (char 0)"}
```

**原因**：`response_format={"type": "json_object"}` 只**降低**了模型不写 JSON 的概率，
不能消除。实测出现过模型回"这段日志信息不足，我无法给出结构化诊断"，
于是 `json.loads` 抛异常，既没有重试，也把异常原文暴露了出去。

同类问题：即使拿到合法 JSON，也**不保证字段齐全**。实测返回过 `{"error_type": 1}`
这种残缺结构，接口照常 200，前端拿到缺字段的对象就会崩
（之前的 `Cannot read properties of undefined` 就是这个成因）。

**修法**：解析 → **校验结构**（必备字段 / 数组字段 / confidence 范围）→
不合格就把问题反馈给模型重试一次 → 仍不合格才抛 `DiagnosisFormatError`，
报错内容里带上模型的原话。重试时用量累加（钱是真花了的）。

> 教训：**"强制 JSON" 不等于 "结构正确"。** 只要模型参与，就要假设它偶尔不听话，
> 并且准备好"发现问题 → 反馈 → 重试"这条路径。

## 20. SDK 的默认超时是 30 分钟

**现象**：一个没被显式设置过的参数。

```
OpenAI SDK 默认：connect=5, read=600, write=600, pool=600，max_retries=2
最坏情况：600 秒 ×（1 次原始 + 2 次重试）≈ 30 分钟
```

而实测一次诊断平均只要 **2 秒**。这个上限毫无意义，只会在故障时让服务无法快速失败 ——
对 SSE 接口来说就是浏览器一直转圈。

**修法**：显式设置 `timeout=httpx.Timeout(connect=5, read=60, ...)` 与 `max_retries=1`，
并做成可配置（`LOGWISE_LLM_TIMEOUT` 等）。

> 教训：**默认值也是设计决策，只不过不是你做的。** 引入任何 SDK 时都该问一句
> "它的默认超时/重试/并发是多少"，而不是等出事才发现。

# 第三次全库排查（21~22）

## 21. `.dockerignore` 排除了运行时必需的数据，而"降级"也降不下来

**现象**：`.dockerignore` 里写着 `data/`，于是容器里没有 `data/fault_cases.jsonl`。

**为什么 pytest 测不出来**：本机有这个文件。所有单元测试、所有集成测试都是绿的，
镜像也能正常构建 —— 只有**真把容器跑起来**才会暴露。

**为什么后果比"知识库读不到"严重得多**：`get_retriever()` 的降级逻辑长这样：

```python
try:
    _retriever = make_retriever(backend, kb_path)      # 读知识库 → 抛
except Exception as exc:
    _retriever = BM25Retriever.from_jsonl(kb_path)     # ← 又去读同一个文件 → 再抛
```

只有一层 `except`，而它的兜底分支又去读**同一个**读不到的文件 —— 异常直接穿出去。
于是容器内 `/stats` 直接 500（它会调 `rag.describe()` → `get_retriever().size()`）。

**修法**（两处都改）：

1. 代码侧：兜底再套一层，最坏情况退化成一个**空知识库**（检索返回空结果，
   诊断照常工作，RAG 本来就默认关闭）。并在 `/stats` 里暴露 `knowledge_base_ok: false`
2. 配置侧：`.dockerignore` 只排除 `data/index/`（可重建的向量索引），
   保留 `data/fault_cases.jsonl` 等运行时文件 —— 去掉索引后 `data/` 只有约 385 KB
3. CI 侧：加**容器冒烟测试**（跑起来打 `/health`、`/stats`，并 `docker exec` 确认知识库在镜像里）

> 教训：**「降级」代码必须自己也能扛住失败。** `except` 分支里做的事如果和 try 里
> 是同一种操作（读同一个文件、调同一个服务），那它大概率也会失败 ——
> 写完要问一句："兜底那段自己抛异常了会怎样？"
>
> 另一条：**单元测试全过 ≠ 跑得起来。** 本机有、容器里没有的文件（或反过来），
> 只有真跑一次才看得出来。

## 22. 文档说"双击即可"，四个脚本其实双击就崩

**现象**：`docs/DEPLOY.md` 写着「`eval_retrieval.py` / `eval_diagnosis.py` / `build_index.py`
都支持双击运行」，但实际只有前两个（加 `build_index.py`）真的做了虚拟环境切换：

| 脚本 | 需要第三方依赖 | 双击能跑吗 |
| --- | --- | --- |
| `demo_parse.py` | 否 | 能（但路径依赖当前目录） |
| `demo_diagnose.py` | openai | ❌ 起不来 |
| `eval_hdfs.py` | 否 | 能（路径依赖当前目录） |
| `eval_diagnosis.py` | openai | ❌ 起不来 |

另外三个问题：

- **路径依赖当前工作目录**：`open("data/sample.log")` 这类写法在 IDE 里
  （工作目录被设成别的）就会找不到文件。
- **`demo_context.py` 自己复制了一份 `_reenter_venv`**：我抽出 `app/launcher.py`
  就是为了避免这事，而那份拷贝还漏了 `print` 的 `flush=True` ——
  用户会看到「按回车键关闭窗口」出现在「[切换] …」前面，顺序是反的。
- **venv 切换的调用位置**：`eval_diagnosis.py` 里如果放到文件末尾的 `__main__` 就太晚了 ——
  模块级的 `from openai import OpenAI` 已经先执行了。必须在 import 之前。

**修法**：所有脚本统一用 `app/launcher.py`；路径统一锚定 `ROOT / "data" / ...`；
venv 切换统一放在 `if __name__ == "__main__" and 任何项目 import 之前`；
`docs/DEPLOY.md` 改成一张「哪些脚本能双击、各自花不花钱」的表。

> 教训：**文档里的承诺要当成 bug 来对待。** "支持双击运行"这句话不是形容，
> 是一个可验证的断言 —— 既然写了，就该有人（或一条 CI）真的去点一下。

## 23. 判定「Key 还没填」的字符串散落在三处，各写各的

**现象**：代码里判断「用户还没填 API Key」的方式，是**匹配中文字符串**，
而且三个地方各写各的：

```
app/diagnose.py:183   key.startswith("sk-在这里")
app/embedding.py:83   key != "在这里填你的智谱Key"    ← 这个字符串 .env.example 里根本不存在
app/run.py:118        key.startswith("sk-在这里") or len(key) < 20
```

实测后果：

| 配置值 | 旧判定 | 应该是 |
| --- | --- | --- |
| `在这里填你的key` | 已配置 ❌ | 占位符 |
| `在这里填你的智谱Key` | 已配置 ❌ | 占位符 |
| `sk-your-key-here` | 已配置 ❌ | 占位符 |
| `sk-shortkey12`（合法短 Key） | 未配置 ❌ | 已配置 |

第一行的后果最隐蔽：它被当成「已配置」，于是真的去调接口，
返回一个 401 之类的鉴权错误 —— **报错内容和「你没填 Key」毫无关系**，很难排查。

`len(key) < 20` 则是反向的错：**把合法的短 Key 拒掉**。长度不是可靠信号，
不同厂商的 Key 长度差别很大；而且误拒比漏拦更难排查（用户明明填了却说没填）。

**修法**：抽出 `app/apikey.py`，判据改成**「含非 ASCII 字符即为占位符」**。

真实 API Key 只用 ASCII 可打印字符，所以这条规则
**不需要维护任何字符串常量**，将来把占位符和注释改成英文也不会失效。
另外再挡掉几种明显的英文写法（`sk-xxx` / `sk-your-key-here` / `<your-key>` / `...`）。
短 Key 不再拒绝，只在启动时给一句提醒。

加了三条回归：

- `TestConsistencyAcrossCallers` —— 同一个值，诊断侧和向量侧的结论必须一致
- `TestLauncherEnvCheck` —— 启动器那条路径（替换 `ROOT` 指向临时目录，不碰真 `.env`）
- `TestNoHardcodedChineseSentinel` —— **AST 级别**检查代码里的字符串字面量，
  禁止再把中文字符串常量加回来（只看代码，不看注释和 docstring，否则说明文字会被误报）

> 教训：**「魔法字符串」是设计缺陷，不是风格问题。** 判定同一件事的常量分散在三处，
> 只要有人改一处（比如为了国际化去改占位符文案），另外两处就会静默失效 ——
> 而且失效方式是「本该拦住的东西被放行」，最难发现的那种。
> 顺便：这条绊线第一次跑就报了两处，但都是**注释里的说明文字** ——
> 于是判据从「全文件文本搜索」收紧到「AST 里的字符串字面量」。
> **绊线自己也要防误报，否则会被当成噪音关掉。**
