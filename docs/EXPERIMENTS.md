## 2. Prompt 设计与 A/B

Prompt 在 `app/prompts.py`，由「分析原则 + 置信度标尺 + 示例约束 + 输出格式 + 4 个 Few-shot」组成。

**设计要点：**

1. **先给分析原则，再给输出格式** —— 只规定格式会让模型为了填满字段而编造内容。
2. **要求输出 `evidence`（日志原文片段）** —— 这是抑制幻觉最有效的一招：
   模型必须为结论指认具体证据，凭空编造的结论很难找出对应原文。
3. **给 confidence 一把握尺** —— 不给标尺时模型会习惯性全给 0.9，置信度就失去区分度。
4. **明确要求区分「根因」与「连带症状」** —— 一次故障会产生多条报错日志，
   只挑第一条会看错方向（见 `data/demo_disk_full.log`）。
5. **允许并鼓励承认信息不足** —— 否则模型宁可瞎猜也不愿说"不知道"。

### 实测的 A/B 数据

用同一批日志对比改版前后（每份日志重复 3 次取均值，模型 `deepseek-chat`）：

| 指标 | 改前 v1（1 个示例） | 改后 v3（4 个示例） | 变化 |
| --- | --- | --- | --- |
| 输入 token | 609 | 2053 | +237% |
| ├ 命中上下文缓存 | 448 | 1856 | — |
| └ **未命中（按全价计费）** | 161 | **197** | **+22%** |
| 输出 token | 180 | 296 | +65% |
| 耗时 | 1499 ms | 2015 ms | +34% |
| **单次成本** | 0.000610 元 | **0.001159 元** | **+90%** |

两个值得注意的结论：

- **输入 token 涨了 237%，但真正按全价计费的只涨 22%** —— 新增内容全在固定前缀里，
  被 DeepSeek 的上下文缓存命中。**因为缓存的存在，Few-shot 其实很便宜，不必吝啬。**
- **输出才是成本大头**：改后单次成本里，输出占 51%、缓存命中输入占 32%、
  未命中输入只占 17%。想控成本应该压输出长度，而不是砍 Few-shot。

## 3. 诊断质量评测

评测集在 `data/eval_cases.json`，共 **38 条**人工标注用例，分五档难度：

| 难度 | 条数 | 考察什么 |
| --- | --- | --- |
| `clear` 常规 | 20 | 能否识别常见故障类型（覆盖资源 / 依赖 / 代码 / 配置 / 网络 / 环境 6 类） |
| `tricky` 根因辨析 | 4 | 真因藏在 `Caused by` 链路里，只看表层异常名会判断错 |
| `vague` 信息不足 | 4 | 日志残缺时，是否诚实给出低置信度，而不是硬猜一个答案 |
| `multi` 多日志连锁 | 6 | 真因在别的日志里，考察上下文聚合是否生效 |
| `noise` 长日志噪音 | 4 | 真因离锚点远、中间夹着无关告警，考察聚合**参数**够不够 |

**为什么要分这么多档**：只有简单用例的评测集会饱和 —— 第一版 20 条常规用例下，
两版 Prompt 都是满分，完全测不出差异。**每加一档，都是因为上一档已经失去区分度。**

评测脚本 `eval_diagnosis.py` 输出三项核心指标：

- **错误类型命中率** —— 是否抓对故障类别（关键词匹配，不苛求措辞）
- **证据可溯源率** —— `evidence` 里的片段能否在原始日志中找到，**这是对幻觉的客观度量**
- **置信度区分度** —— 清晰用例的平均置信度减去信息不足用例的平均置信度。
  一个只会给 0.9 的模型，这个值为 0

### 3.1 Prompt v1 → v3 的 A/B

同一套 28 条用例，对比 Prompt 改版前后（`--from-git HEAD` 加载旧版）：

| 指标 | 改前 v1 | 改后 v3 | 说明 |
| --- | --- | --- | --- |
| 错误类型命中率 | 24/24 = 100% | 24/24 = 100% | **饱和了，不具区分度** |
| 输出格式合规率 | 28/28 = 100% | 28/28 = 100% | 同上 |
| 含 evidence 字段 | 0/28 = 0% | 28/28 = 100% | v3 新增字段 |
| 证据可溯源率 | 不适用 | **59/59 = 100%** | 零编造证据 |
| **低置信度诚实率** | **2/4 = 50%** | **4/4 = 100%** | ← 真正的提升 |
| **置信度区分度** | **+0.262** | **+0.459** | ← 提升 75% |
| 单次成本 | 0.000602 元 | 0.001081 元 | +80% |

**怎么读这张表：**

1. **「错误类型命中率」两边都是满分 —— 这个指标饱和了，不能用来判断 Prompt 好坏。**
   日志里的异常类名（`OutOfMemoryError`、`No space left on device`）本身信息量很足，
   模型只需要读懂英文再归类。这也说明**评测集本身要设计得有区分度，否则测了等于没测**。
   第一版 20 条用例两版都是 100%，补了 `tricky` / `vague` 两档之后才拉开差距。

2. **真正拉开差距的是置信度校准。** 旧 Prompt 在 4 条信息不足的日志里，
   有 2 条给出了 0.75 和 0.85 的高置信度 —— 只有一行 `ERROR 夜间任务执行失败` 的日志，
   它也敢打包票。新 Prompt 把这 4 条全部压到 0.7 以下（0.30 / 0.30 / 0.45 / 0.62）。

3. **新 Prompt 在清晰用例上反而更保守**（0.91 → 0.85）。这不是变差 ——
   而是置信度标尺起作用了，不再无脑给高分。一高一低，区分度自然从 0.262 拉到 0.459。

**结论**：这次改动让成本上升约 80%，换来的不是"识别得更准"（那本来就满分），
而是**「知道自己什么时候不知道」**。对一个运维诊断工具来说，
在信息不足时敢说"我不确定"，比永远给一个笃定的错误答案更有价值。

### 3.2 评测集的数据泄漏（已修复）

设计检索功能之前先查了一件事，结果发现问题：38 条评测用例里有 3 条与 Few-shot 示例撞了场景。

| 用例 | 撞上的示例 | 泄漏形态 |
| --- | --- | --- |
| `res-01` 磁盘空间不足 | 示例2 | **两行日志逐字相同**（`No space left on device`、`at java.base/java.io.FileOutputStream.writeBytes`） |
| `cfg-03` 配置项类型不合法 | 示例4 | **异常消息骨架相同**：`IllegalStateException: Failed to bind properties under '?' to ?`，只有参数不同 |
| `bug-04` 空指针异常 | 示例3 | 同类故障，措辞略有差异 |

这三条在历次评测里都是满分，但它们考的其实是「能否对照示例抄答案」。

**修法**：换成 Few-shot 未覆盖的故障类型 ——
`res-01` → 磁盘配额超限（`Disk quota exceeded`）、
`cfg-03` → YAML 语法错误、
`bug-04` → 并发修改异常。

**并加了绊线**：`test_no_shared_exception_template` 会把异常消息归一化成骨架
（抹掉引号内的取值、类名、数字）再比对，撞车即失败。已验证把它改回泄漏版本会立刻报警。

## 4. 上下文聚合

### 4.1 已量化的短板：多日志上下文缺失

`_pick_target()` 原本**只挑第一条 ERROR** 送进模型，其余日志全部丢弃。
评测集里有 6 条专门为此设计的用例：真因藏在 WARN / INFO 行或后面的日志里，
第一条 ERROR 只看到连带症状。

同一批用例，分别测「现状」与「把全部日志都送进去（天花板）」：

| 指标 | 现状（只送第一条） | 天花板（送全部） | 差距 |
| --- | --- | --- | --- |
| 命中率 | **1/6 = 16.7%** | **6/6 = 100%** | **+83.3 个百分点** |
| 平均输入 token | 2010 | 2125 | +5.7% |
| 平均输出 token | 252 | 323 | +28% |
| 单次成本 | 0.001089 元 | 0.001217 元 | **+11.8%** |

**这条测量的价值在于它把结论钉死了**：差距 83 个百分点说明问题
**完全出在上下文缺失，而不是模型能力不足**；而成本只涨 12%，
说明「把多条日志一起送进去」是一件几乎免费的事。

几个典型失败案例（现状 → 天花板）：

| 用例 | 现状给出的结论 | 看到全部日志后的结论 |
| --- | --- | --- |
| Pod 驱逐 | 网关调用订单服务连接被拒绝 | 节点内存不足触发 Pod 驱逐 |
| 磁盘写满 | 上游依赖返回 503，服务不可用 | 磁盘写满导致本地缓存子系统不可用 |
| 主从切换 | 数据库连接池获取连接超时 | 主库故障触发主从切换 |
| 上游发版 | 调用会员服务返回 404 | 服务发布后接口路径不兼容 |

### 4.2 修复方案：日志上下文聚合（`app/context.py`）

分层聚合，**不做语义关联，每一层都不依赖日志格式**：

1. **锚点** —— 必含。第一条 CRITICAL/ERROR；没有则第一条 WARN；再没有则第一条
2. **窗口内的异常日志** —— 锚点前后 K 条以内、且级别 ≥ WARN
3. **窗口内的普通日志** —— 锚点前后 K 条以内（比如发布通知这类 INFO）
4. **窗口外的异常日志** —— 范围里其他 WARN/ERROR（离得远但可能是真因）

超过上限 M 条时按上述优先级淘汰，**锚点无论如何都保留**。
最终**按原始顺序输出** —— 时间线本身就是诊断线索。

**为什么不做时间裁剪**：曾考虑「跨度超过 N 分钟就裁到锚点附近」，但用例 `multi-03` 里
证书续期失败的 WARN 在 06:00、TLS 握手失败的 ERROR 在 09:14，跨度 3 小时却确实是
同一次故障。**用户既然把这段范围粘贴进来，说明他已经做过预筛选**，
我们的任务是在这个范围里挑相关的，而不是再按时间裁一遍。

### 4.3 参数扫描

评测集共 **38 条**，其中 10 条专门用来区分聚合参数：

- `multi-01 ~ 06`（多日志连锁）：真因藏在其他日志里，考验**有没有做聚合**
- `noise-01 ~ 04`（长日志噪音）：真因离锚点较远、中间夹着无关告警，
  考验**窗口 K 够不够大、上限 M 够不够留得住真因**

四组参数各跑一轮完整评测（同一模型）：

| 组 | 参数 | 多日志(6) | 噪音(4) | **上下文类小计(10)** | 常规档(24) | 整体 | 平均输入 token | 单次成本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A | 关闭聚合（旧行为） | 1/6 | 0/4 | **1/10 = 10.0%** | 24/24 | 73.5% | 2013 | 0.001102 元 |
| B | 窗口 ±2 / 上限 8 | 6/6 | 0/4 | **6/10 = 60.0%** | 24/24 | 88.2% | 2066 | 0.001142 元 |
| C | 窗口 ±4 / 上限 12 | 6/6 | 2/4 | **8/10 = 80.0%** | 24/24 | 94.1% | 2086 | 0.001162 元 |
| D | 窗口 ±8 / 上限 20 | 6/6 | 4/4 | **10/10 = 100.0%** | 24/24 | 100.0% | 2103 | 0.001139 元 |

> **当前默认值是 D（±8 / 上限 20）** —— 这是扫描结果选出来的，不是拍脑袋定的。
> 对应的回归测试：`tests/test_eval_dataset.py::TestDefaultParamsCoverRootCause`
> 会校验「默认参数能覆盖所有上下文类用例的真因」，**把默认值调小会立刻测试失败**，
> 不用等到下次跑评测（约 5 分钟 + 花钱）才发现。

**这是一条干净的单调梯度：10% → 60% → 80% → 100%。**

四个结论：

1. **聚合本身是决定性的**：A → B 一步就把多日志档从 1/6 拉到 6/6。
2. **参数确实有影响**：60% → 80% → 100%，而且和用例的设计预期完全吻合 ——
   `noise-01/03` 需要更大的窗口/上限，`noise-02/04` 需要最大的那一组。
3. **成本几乎不变**：四组输入 token 相差不到 5%，D 组（上限最大）的单次成本
   甚至比 C 组还低 —— 差异在缓存命中的波动范围内。
4. **常规档 24/24 全部保持满分**：上下文变长没有把简单场景搞坏。

> **第一版结论的修正**：在只有 34 条用例（无噪音档）时，B / C / D 得分完全相同，
> 当时只能"取中间值求稳"。补上噪音用例之后梯度才显现出来 ——
> **这正好说明：评测集没有区分度时，参数扫描等于白跑。**
> 用例设计上有个细节值得一提：最初把关键词写成 `stock`，但锚点的类名恰好是
> `StockClient`，导致关键词泄漏、用例失去测度能力。现在这条已固化为一回归测试
> （`test_root_cause_keywords_never_leak_into_anchor`）。

## 5. RAG 故障案例库

> 状态：**检索端、注入端、向量后端均已实现并量化**。
> 两组 A/B 的结论一致 —— **暂不开启**（默认 `LOGWISE_RAG_MODE=fixed`、`LOGWISE_RETRIEVER_BACKEND=bm25`）。

### 5.1 为什么把检索单独测

RAG 由**检索**与**注入**两段组成。检索找错了案例，Prompt 再讲究也救不回来。
而检索质量**完全不需要调用大模型**就能测 —— 有没有召回同类案例是纯本地可算的。
所以这一步能在花任何钱之前先把关：检索不过关，就不必谈注入。

### 5.2 检索质量实测（零成本）

知识库 53 条、16 个故障类别；评测 32 条用例（6 条故意信息不足的已排除）：

| 指标 | 结果 | 随机基线 |
| --- | --- | --- |
| Recall@3 | **31/32 = 97.1%** | ≈6% |
| Recall@5 | **32/32 = 100%** | ≈6% |
| Precision@1 | **29/32 = 85.3%** | ≈6% |
| MRR | **0.904** | — |
| 完全未召回到同类 | **0/32 = 0%** | — |

> 随机基线 = 1 / 故障类别数（16 类），即随机返回一条命中的概率。

运行方式：`python eval_retrieval.py`

剩余少数 top-1 不准的都属**合理混淆**，且全部落在 top-3 内：
`res-03`（`FileNotFoundException (Too many open files)`）与 `perm-04`（同模板但原因是 `Permission denied`）、
`bug-03`（线程死锁）与 `db-06`（数据库死锁）、`tricky-03`（表层 OOM、真因是无限递归）。

### 5.3 两个真实踩到的坑

**① query 侧词频被线性放大**

长日志噪音用例里有 10 条「健康检查通过」。早期实现按出现次数累加，该词权重被放大 10 倍，
把一条恰好含相同噪音的案例顶到检索第一（**760 分**），而真正该命中的案例排第 4。

修法：**query 侧二值化**（用 `set` 而不是 `Counter`）。检索只关心"出现了哪些错误"，
不关心同一个词重复几次 —— 词频的作用体现在文档侧（`tf`），不体现在查询侧。

**② 无信息量的行没有被过滤**

同上。这类行在故障上下文里没有任何区分度，却能在数量上压倒异常行。
现在在**查询与文档两端**的 token 化阶段都跳过健康检查 / 指标上报 / 心跳这类行。

两个修正加上补充案例的合计效果：

| 指标 | 修正前 | 修正后 |
| --- | --- | --- |
| Recall@3 | 81.2% | **97.1%** |
| Precision@1 | 62.5% | **85.3%** |
| MRR | 0.810 | **0.904** |
| 完全未召回 | 3/32 | **0/32** |

### 5.4 注入 Prompt 的三组 A/B：**成本涨 53%~81%，准确率提升 0**

| 组 | 注入策略 | 命中率 | 常规档 | 上下文类 | 输入 token | **缓存命中率** | 单次成本 | vs 基线 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **A** | `fixed` 固定示例 | 34/34 = 100% | 24/24 | 10/10 | 2104 | **90%** | 0.001138 元 | — |
| **B** | `dynamic` 纯检索 | 34/34 = 100% | 24/24 | 10/10 | 1761 | **39%** | 0.001745 元 | **+53%** |
| **C** | `hybrid` 两者都用 | 34/34 = 100% | 24/24 | 10/10 | 3142 | 64% | 0.002053 元 | **+81%** |

38 条用例、同一模型、同一上下文聚合参数、同一时间窗口，各跑一轮。

**命中率三组完全相同，说明这套评测集测不出 RAG 的价值。**

### 5.5 一个反直觉的成本发现

B 组的输入 token 比 A 组**少 16%**，成本却高 **53%**。原因是上下文缓存：

| 组 | 成本构成（缓存命中输入 / 未命中输入 / 输出） |
| --- | --- |
| A | 33% / 18% / 49% |
| B | 8% / **61%** / 31% |
| C | 20% / 55% / 25% |

DeepSeek 会缓存**重复出现的 Prompt 前缀**，命中部分单价只有 1/5。
固定示例每次请求都一样 → 90% 命中；检索到的案例每次都不同 → 缓存前缀被打断，只能按全价算。

**结论：动态注入的内容在缓存机制下是"结构性更贵"的。**
这是设计 RAG 时容易忽略的一点 —— 只看 token 数量会得出完全错误的成本判断，
必须看**命中缓存的比例**。

### 5.6 为什么 RAG 在这里没有产生价值

不是因为 RAG 本身没用，而是**这套知识库提供不了模型不知道的信息**。

知识库里是 Redis 连不上、磁盘写满、NPE 未判空这类**通用故障模式** ——
这些模型本来就会。RAG 的价值在于注入**私有知识**：
自研组件的错误码含义、公司内部的处置规范、只有你们踩过的坑。

现在这个组合相当于：把模型已知的常识当作参考资料再喂它一遍，然后期待它变强。

**判断方法只有一句：这份资料，模型是不是本来就知道？**
是 → RAG 没有价值；不是 → RAG 立刻有价值。

> **诚实说明**：`vague` 类的"低置信度诚实率"出现过 A=75% / B,C=100% 的差异，
> 但**不能据此认为 RAG 提升了置信度校准** —— 该档只有 4 条用例，
> A 组是其中一条（`vague-03`）返回了非数值置信度导致判定失败。
> 单次运行、4 条样本，这个差异在噪声范围内。要下这个结论需要重复多轮。

### 5.7 所以默认保持 `fixed`

`LOGWISE_RAG_MODE=fixed`。整套检索与注入代码都在，随时可切换做实验：

```bash
python eval_diagnosis.py --rag-mode dynamic   # 或 hybrid
```

要让 RAG 真正产生价值，下一步应该往知识库里放**真正私有的知识**，
或者换一个「模型不可能知道答案」的评测任务 —— 而不是继续调 Prompt 与检索参数。

### 5.8 知识库的隔离原则

做 RAG 最容易出的错是**把答案抄进课本再考同一张卷子**。因此：

- 知识库案例与评测用例**不得有相同的业务行**（带自定义包名或中文业务描述的行）
- 知识库案例与 Few-shot 示例同样不得重复（否则等于重复注入，白烧 token）
- 知识库定位为「历史故障」，时间戳统一放在 2025 年，与评测集（2026 年）错开
- 以上三条都有测试守着（`tests/test_knowledge_base.py`）

> **判据说明**：JDK / 中间件的标准堆栈帧与通用异常消息
> （`at java.base/java.io.File.createNewFile(File.java:1035)`、
> `java.lang.OutOfMemoryError: Java heap space`、`The MySQL server is running with the --read-only option`）
> **不算泄漏** —— 它们是语言与库的固定输出，任何同类故障都会出现，且不含业务上下文。
> 因此判据从「整行重复」改为「业务签名重复」，否则会大量误报。

## 6. 三后端检索对比

### 6.1 为什么换了一家厂商做向量

DeepSeek 不提供 embedding 接口（实测 `POST /embeddings` 返回 **404**，模型列表只有对话模型），
所以向量化用了另一家。这不是凑合 —— **一个项目用多家服务是常规做法**，
诊断仍走 DeepSeek，只有向量化走别的。

代码做成了**通用 OpenAI 兼容客户端**，换厂商只改 `.env` 三行：

```
EMBEDDING_BASE_URL=https://open.bigmodel.cn/api/paas/v4
EMBEDDING_API_KEY=...
EMBEDDING_MODEL=embedding-3
```

智谱 / 阿里百炼 / 硅基流动 都是这个格式，代码不用动。

| 后端 | 说明 | 成本 |
| --- | --- | --- |
| `bm25` **（默认）** | 词法检索，纯本地、零依赖 | 零 |
| `dense` | 向量余弦相似度 | 建索引约 0.005 元 |
| `hybrid` | 两者用 RRF 融合 | 同上 |

**为什么融合用 RRF 而不是分数加权**：BM25 的分数是 0 到 +∞ 的无界值，
余弦相似度在 -1~1 之间 —— 两者尺度完全不同，直接相加等于让 BM25 单方面主导结果。
RRF 只看排名，天然免疫尺度问题，这是它成为检索工程通用做法的原因。

**未配置 Key 时的行为**：服务正常启动，自动降级到 BM25，
`/stats` 里能看到降级状态与原因 —— 向量服务没配好不该让整个诊断服务起不来：

```json
"retriever": { "requested": "dense", "actual": "bm25", "degraded": true, "reason": "..." }
```

**索引不落版本库**：`data/index/` 在 `.gitignore` 里（约 1 MB 浮点数，可随时重建）。
底层的向量缓存按 `(模型, 文本)` 哈希去重，重复运行不会重复计费。

### 6.2 实测结果：**BM25 仍然最好，Hybrid 没有增益**

38 条用例、同一套 query（都经过上下文聚合），各跑一轮：

| 后端 | Precision@1 | Recall@3 | Recall@5 | MRR | 未召回 | 每条耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| **`bm25`（默认）** | **85.3%** | **97.1%** | **100%** | **0.904** | **0** | **0.4 ms** |
| `dense` | 79.4% | 85.3% | 91.2% | 0.912 | 3 | ~300 ms |
| `hybrid` | 76.5% | 97.1% | 100% | 0.855 | 0 | ~300 ms |

跑之前我猜"dense 会低于 bm25、hybrid 会接近 bm25" —— **前一半猜对，后一半猜错**。

#### ① Dense 的 MRR 反而更高，但召回不全

dense 的 MRR 是 0.912，**高于** bm25 的 0.904 —— 它找对的那些案例排名更靠前。
但 Recall@3 只有 85.3%，整整漏了 3 条。属于"有把握的地方更准，但会整体漏掉一部分"。

#### ② Hybrid 融合后 Precision@1 与 MRR 都降了

Recall@3 持平（97.1%），但 Precision@1 从 85.3% 掉到 76.5%，MRR 从 0.904 掉到 0.855。

原因：**RRF 偏向「两个后端都认可」的文档**。而 dense 排第一的往往是
「语义上像、根因却不同」的案例（例如把「503 Service Unavailable」匹配到 upstream，
而不是真正的 disk）。这类结果与 BM25 的某条一同出现时，
会把 BM25 原本排第一的正解挤下去 —— 融合在这里不是取长补短，而是稀释。

#### ③ 最能说明问题的是 noise-03 / noise-04

| 用例 | 真因 | BM25 | Dense | Hybrid |
| --- | --- | --- | --- | --- |
| `noise-03` | 文件被外部进程锁定 | **第 1 名** | **完全没找到** | 第 3 名 |
| `noise-04` | 同上 | **第 1 名** | **完全没找到** | 第 3 名 |

这两条 query 里夹了 10~18 条「缓存命中率低」的无关告警。
向量的语义被这些噪音稀释了（整段文本的整体语义偏向"缓存有问题"）；
而 BM25 靠精确 token（`锁定`、`文件`、`外部进程`）依然一击命中。

**这就是「日志检索靠精确 token，不靠语义」最直接的证据。**

#### ④ 成本与耗时

| 项 | 数值 |
| --- | --- |
| 建索引（53 条） | 11,262 token ≈ **0.0056 元** |
| 本次全部评测（含两轮 query 向量化） | 约 **0.016 元** |
| Dense 每条 query 的增量耗时 | **~300 ms**（BM25 是 0.4 ms，慢约 780 倍） |

> ⚠️ `--compare` 输出里 hybrid 显示 5.2 ms/条是**被低估**的：
> dense 阶段已经算过同样的 query 向量，hybrid 阶段直接命中了缓存。
> 单独冷启动跑 hybrid 的真实耗时约为 `BM25 + 300 ms`。

### 6.3 所以默认保持 `bm25`

与 RAG 那次的结论一致：**先量化，再决定**。这次的数据同样没有支持"换更复杂的方案"。
三个后端都留着，随时可以复跑：

```bash
python build_index.py               # 建索引（约 0.005 元；已缓存条目自动跳过）
python eval_retrieval.py --compare  # 三后端并排对比
```
